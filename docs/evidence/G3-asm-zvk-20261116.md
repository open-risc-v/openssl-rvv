# openssl RISC-V Zvk 汇编 A/B（第八个上游自带向量实现的包）

- 日期：2026-11-16
- 上游：`openssl/openssl` @ `3f11738c…`（OpenSSL 4.2.0-dev）
- 目标：`linux64-riscv64`，`no-shared no-tests no-docs`
- 两侧 C 代码编译选项完全相同：`-O3 -march=rv64gc`（**无向量**）
- 唯一变量：**是否启用汇编内核**（on 侧默认 `asm_arch=riscv64`，off 侧 `no-asm`）
- 真机：SpacemiT K3 / Bianbu，`Linux k3 6.18.3 riscv64`，RVV 1.0 + `zvkned/zvknha/zvknhb/zvkb/zvkg/zvks`

## 1. 为什么这个包是"自带"

普查判据（`grep -rl "__riscv_v\|riscv_vector"`）在 openssl 上一处都不命中，但它的**汇编层**早就有 RISC-V 向量加密实现：

```
crypto/aes/asm/aes-riscv64-zvkned.pl
crypto/aes/asm/aes-riscv64-zvkb-zvkned.pl
crypto/aes/asm/aes-riscv64-zvbb-zvkg-zvkned.pl
crypto/sha/asm/sha256-riscv64-zvkb-zvknha_or_zvknhb.pl
crypto/sha/asm/sha512-riscv64-zvkb-zvknhb.pl
crypto/sha/asm/sha256-riscv64-zbb.pl   /  sha512-riscv64-zbb.pl
```

`crypto/aes/build.info` 里 `IF[{- $target{asm_arch} eq "riscv64" -}]` 无条件把这几个 `.s`
编进 `libcrypto.a`，运行时再按 `hwprobe` 的能力选择。所以**只要 target 是
`linux64-riscv64`，什么都不用改**——这正是"上游自带"的判据要点：`__riscv_v` 只覆盖
intrinsics，覆盖不到 perlasm。

这也说明之前的 SIMD 普查方法有盲区：**perlasm 类上游（openssl / x264 / libvpx）要先看
`*/asm/*riscv*` 目录**，不能只 grep intrinsics 宏。

## 2. 编入情况（on 侧 `libcrypto.a`）

```
43 个 riscv64_zvk* 符号
libcrypto-lib-aes-riscv64-zkn.o
libcrypto-lib-aes-riscv64-zvbb-zvkg-zvkned.o
libcrypto-lib-aes-riscv64-zvkb-zvkned.o
libcrypto-lib-aes-riscv64-zvkned.o
libcrypto-lib-aes-gcm-riscv64-zvkb-zvkg-zvkned.o     ← 连 GCM 也在
libcrypto-lib-sha256-riscv64-zbb.o
```

C 侧两侧都是 `-march=rv64gc`，没有任何向量代码，因此差异只能来自汇编。

## 3. 功能

64 KiB 输入，AES-128-CBC 加密 → 解密回环 + AES-128-CTR + SHA-256：

```
sha256=b5c66c4dfe737e31145c2cf0a52a7ceadf0045f26dffd6ef3414b0f9d3687365
fnv_ct =cc18494f5e673a69      (CBC 密文)
fnv_ctr=5c61394dab555006      (CTR 密文)
```

on/off 两侧**逐字节一致**（真机 `cmp` 通过），且与之前 G2 基线的 `fnv_ct=cc18494f5e673a69`
一致。

## 4. 真机性能（64 KiB，5 轮 × 每轮内部 best-of-5）

| 路径 | off（no-asm） | on（汇编） | 比值 | 吞吐（on） |
|---|---|---|---|---|
| AES-128-CBC 加密 | 7.03–7.07 ms | **0.051 ms** | **≈138×** | 1.23 GB/s |
| AES-128-CBC 解密 | 7.43 ms | **0.052 ms** | **≈143×** | 1.21 GB/s |
| AES-128-CTR | 7.10–7.12 ms | **0.025 ms** | **≈284×** | 2.51 GB/s |
| SHA-256 | 0.662–0.665 ms | **0.078 ms** | **8.5×** | 0.80 GB/s |

数字极其稳定（off 侧波动 <1%，on 侧几乎无波动）。

## 5. 归因（三重证据）

1. **符号层**：`aes-riscv64-zvkned.o`、`aes-gcm-...zvkned.o`、`sha256-riscv64-zbb.o` 全部在
   `libcrypto.a` 里（43 个 zvk 符号）。
2. **qemu 对照**：qemu 没有 Zvkned、但有 Zbb。此时 on 的 SHA-256 是 **0.324 ms vs off 0.565 ms
   = 1.74×**（Zbb 汇编确实在跑）；而 CBC/CTR 两侧一样慢（4.80 vs 4.97 ms）——说明
   **Zvkned 路径在 qemu 里根本没执行**，只可能由真机的 zvkned 硬件贡献。
3. **量级一致**：同机 libgcrypt 的 Zvkned AES-CTR 内核是 39.4×（对比更快的 bitslice C）。
   openssl 的 C 实现（`OPENSSL_AES_CONST_TIME` 常数时间版本）本身更慢，所以倍数更大
   但量级同源。

**未能做到的隔离**：`OPENSSL_riscvcap` 环境变量在这一版上只要被设置就整体退回保守路径
（试过 `rv64gc` / `rv64gcv` / `rv64gcv_zvkned` / `rv64gcv_zvkned_zvkb_zvkg` / `zvkned` /
`v_zvkned` 六种写法，全部 ~7 ms），因此拿不到"只开 zvkned、其余不变"的单扩展对照。
上面的归因是由 1+2+3 共同闭合的，不是单一实验。

## 6. 这对 G2/G3 口径的影响

openssl 之前停在 G2 是因为"交叉基线通过、但没碰向量"。现在证明**它的向量实现不需要我们
写**，只需要正确的 target 与 `asm_arch`。剩余工作不是内核开发，而是：

- 补 AES-256-GCM / SHA-512 / SHA-3 的同类 A/B（`aes-gcm-riscv64-zvkb-zvkg-zvkned.o`
  已在库里，说明 GCM 也走向量）；
- 与 `-march=rv64gcv` 的 C 向量化对照（当前 C 侧刻意用 `rv64gc` 以隔离汇编变量）。

## 7. 复现

```bash
# on
CC=riscv64-linux-gnu-gcc perl Configure linux64-riscv64 --prefix=$P/on \
  --openssldir=$P/ssl no-shared no-tests no-docs -march=rv64gc
make -j8 build_sw && make install_sw
# off
perl Configure linux64-riscv64 --prefix=$P/off --openssldir=$P/ssl \
  no-shared no-tests no-docs no-asm -march=rv64gc
make -j8 build_sw && make install_sw
# harness
riscv64-linux-gnu-gcc -O2 -march=rv64gc -I $P/<side>/include test/pkg_ossl.c \
  $P/<side>/lib/libcrypto.a -ldl -lpthread -static -o harness_<side>
# 真机
harness_off|on <out.bin|/dev/null> <reps>     # 计时写 stderr
```

## 8. 补充：AES-GCM 与 SHA-512（同轮同库，2026-11-16 续测）

首版只测了 CBC / CTR / SHA-256，GCM 与 SHA-512 的汇编对象虽在库里但没走。本轮把探针
扩到 6 条路径，同一对 `libcrypto.a`、同一台机器、三轮重复：

| 路径 | off（no-asm） | on（Zvk 汇编） | 倍率 |
|---|---|---|---|
| AES-128-CBC 加密 | 6.736 / 6.787 / 6.873 ms | **0.051 ms** | **≈132×** |
| AES-128-CBC 解密 | 7.347 / 7.347 / 7.367 | **0.052 ms** | **≈141×** |
| AES-128-CTR | 6.932 / 7.101 / 6.993 | **0.025 ms** | **≈277×** |
| SHA-256 | 0.662 / 0.662 / 0.664 | **0.078 ms** | **≈8.5×** |
| **AES-256-GCM**（AAD 16B + IV 12B） | 9.905 / 10.064 / 10.037 | **0.035 ms** | **≈287×** |
| **SHA-512** | 0.368 / 0.369 / 0.369 | **0.099 ms** | **≈3.7×** |

六条路径的输出全同，`cmp` 得 `BYTES_SAME`：

```
fnv_ct=cc18494f5e673a69        fnv_ctr=5c61394dab555006
fnv_gcm=277da5ef19ec13c4       tag=be1f5baad4e36232b20cd367555be2bf
sha256=b5c66c4dfe737e31145c2cf0a52a7ceadf0045f26dffd6ef3414b0f9d3687365
sha512=b9e2c354b5c84895da86eb5860142d6e0a2599e9d4b88c0f55bb83f386a985fe
       55592f8ae49ed7939f64563af15d5d105013f3cfeeed22a06231aebedda1ea48
```

**归因证据（`nm`，on 侧 `libcrypto.a`）**：

```
gcm_init_rv64i_zvkg        gcm_gmult_rv64i_zvkg       gcm_ghash_rv64i_zvkg
gcm_init_rv64i_zvkg_zvkb   gcm_*_rv64i_zvkb_zvbc（另有 Zvbc 变体）
sha256_block_data_order_zvkb_zvknha_or_zvknhb
sha512_block_data_order_zvkb_zvknhb
libcrypto-lib-aes-gcm-riscv64-zvkb-zvkg-zvkned.o   （对象在库中）
```

即 **GCM 的 287× 由两部分叠加**：AES 轮走 `zvkned`，GHASH 走 `zvkg` 的 `vgmul`
（off 侧 GHASH 是逐块 128-bit 多项式乘法的纯 C）。SHA-512 走 `zvknhb`，
增益（3.7×）低于 SHA-256（8.5×），因为 SHA-512 在 64 位机上的标量实现本来就更接近
理论吞吐（每轮 64 位运算），向量化的相对空间更小。

**口径提醒**：
- 这些倍率是 **Zvk 汇编 对 无向量 C**，不是"RVV 通用向量化"，报告里不能写成 RVV 让 AES 快 287 倍。
- 两侧 C 代码同为 `-O3 -march=rv64gc`，唯一变量是 `no-asm`；`cipher=` 行里 on 侧多出的
  `-Wa,--noexecstack` 是汇编配置的副产物，不影响 C 代码生成。
- 仍然**无法做单扩展隔离**：`OPENSSL_riscvcap` 只要被设置就整体退回保守路径
  （试过 10 种写法，结果一律 ~7 ms，与 off 侧同量级）。因此 GCM 的增益只能通过
  `nm` 符号 + off/on 对照归因，不能证明"AES 部分是 X 倍、GHASH 部分是 Y 倍"。
